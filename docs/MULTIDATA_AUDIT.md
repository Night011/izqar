## Проверка утечек и доступности признаков

Model Registry доступен по защищённому `GET /api/v1/model/registry`. Он показывает четыре активных артефакта и локальную историю отчётов из `backend/models/experiments/`, включая отчёты без модели; JSON читается без исполнения pickle. История отражает файлы на данном компьютере, а не централизованное хранилище организации. Изменение файла меняет его SHA-256, но не делает исходный файл автоматически доверенным.

- PaySim `isFraud` — только метка. `isFlaggedFraud`, `newbalanceOrig`, `newbalanceDest`, идентификаторы счетов и `step` не передаются модели. `oldbalanceOrg`/`oldbalanceDest` трактуются как остатки до операции; перед применением к иному источнику требуется подтвердить, что они реально доступны до решения. Важность категорий `type` очень высока, что требует проверки устойчивости на новых типах и смещении распределения.
- IEEE-CIS `isFraud`, `TransactionID`, `TransactionDT` исключены из X. `TransactionDT` задаёт относительное время для разделения. Препроцессинг обучается только на train. Анонимизированные группы C/D/V и identity требуют предметной проверки времени доступности; отсутствие явной цели в названии не доказывает отсутствие скрытой утечки.
- BAF Base `fraud_bool` используется только как y, `month` только для временного разделения. `device_fraud_count`, `days_since_request`, `credit_risk_score` и не проверенные исторические агрегаты исключены. Важность `housing_status_BA` составляет 36.247% gain, `device_os_windows` — 14.544%; это повод проверить устойчивость на другом периоде и доступность признаков в момент заявки, а не доказательство утечки. Анонимизированные значения не следует трактовать как реальные социальные группы.
- IBM AML `Is Laundering` используется только как y; два `Account`, сырые идентификаторы банков и `Amount Received` исключены из ML-признаков. Текущие `Amount Paid`, валюты, формат, время и сравнение банков доступны при операции по принятому сценарию; это предположение требует проверки для реальной интеграции. У финальной модели наибольшая важность у `Payment Format=ACH` (33.1015% gain), поэтому связь с особенностями синтетического генератора и сдвигом форматов нужно исследовать на новых данных. Графовые исторические признаки в этой версии ML-модели отсутствуют.
- Unified schema дополнительно отклоняет все перечисленные целевые поля, post-event поля, идентификаторы счетов PaySim (`nameOrig`, `nameDest`), `step`, BAF month/historical fields и IBM `Amount Received` ещё до загрузки preprocessing. Проверка Registry и загрузчика покрыта тестами: недоверенный манифест с такими полями не становится доступным для инференса.
- Ни одна модель не даёт подтверждённую вероятность банковского мошенничества; сохранённый скор не калиброван на реальном потоке.

## Validation-only анализ устойчивости

Команды из `backend/` записывают отдельные отчёты в игнорируемый Git каталог и отказываются перезаписывать существующие файлы:

```powershell
.\.venv\Scripts\python.exe scripts\audit_ieee_validation.py --data-dir data\ieee --model models\ieee_final_v2.joblib --output models\experiments\ieee_validation_audit_NEW.json
.\.venv\Scripts\python.exe scripts\audit_paysim_validation.py --data data\paysim\PS_20174392719_1491204439457_log.csv --model models\paysim_model_v2.joblib --output models\experiments\paysim_validation_audit_NEW.json
```

IEEE-CIS локальный аудит текущего артефакта воспроизвёл исходные validation-метрики ровно. По последовательным третям validation PR-AUC: **0.562696 → 0.432106 → 0.366580**; ложные тревоги на 10 000: **86.7 → 85.0 → 128.0**. Для `ProductCD=W` recall при фиксированном пороге — **0.089562**. Это признаки неоднородности и возможного дрейфа, а не доказательство причины. Искусственное обнуление числовых полей у 10% строк снизило PR-AUC с 0.455173 до 0.420437. Эксперимент с невиданной категорией `DeviceInfo` дал PR-AUC 0.454045. Эти стресс-проверки не моделируют реальные будущие данные.

PaySim validation-аудит переносимого v2 показал неоднородность по типу операции: recall для `CASH_OUT` **0.368421**, для `TRANSFER` **0.964912**; число ложных тревог на 10 000: **0.264** и **29.804** соответственно. По последовательным третям validation PR-AUC **0.485466 → 0.633945 → 0.668811**; различие связано в том числе с частотой размеченного класса. Замена типа операции невиданной категорией снизила PR-AUC до **0.385211**. Это диагностические срезы уже использованной validation, а не независимая оценка будущего потока.

Проведён validation-only эксперимент с дополнительными `C3`, `C5`, `V4`–`V10` при тех же 180 деревьях и том же train-периоде. При бюджете до **100 ложных тревог на 10 000** получены Precision **0.578244**, Recall **0.398422**, F1 **0.471779**, PR-AUC **0.466359**, FP **884** на 88 581 validation-операции. У текущего core-артефакта на той же validation Precision **0.569343**, Recall **0.384615**, F1 **0.459094**, PR-AUC **0.455173**, FP **885**. Разница небольшая и может отражать отбор по validation; новый набор признаков не объявлен победителем и не проходит прежний test. Отчёты сохранены отдельно в `backend/models/experiments/` (вне Git).

## Мультитаск-модель

14 ноября 2026 в Kaggle выполнен CPU validation-only запуск настоящей совместной сети: четыре специфических входных encoder, общий 32→16 backbone и четыре независимые головы. Аудит градиента общего блока ненулевой для всех задач: PaySim `0.21800983`, IEEE-CIS `0.01058507`, BAF `0.04945304`, IBM AML `0.13348407`; это подтверждает, что общий блок получал обучающий сигнал от каждого источника. На 75 000 validation-записях каждой задачи получены: PaySim PR-AUC `0.037139` / F1 `0.050000`, IEEE-CIS `0.188936` / `0.265172`, BAF `0.137183` / `0.223346`, IBM AML `0.013440` / `0.037538`.

Эти числа не являются final test, не калиброваны и не доказывают замену специализированных моделей. Проверенный ZIP установлен локально 14 ноября: его четыре компонента прошли SHA-256 проверку, `/api/v1/model/status` загрузил Unified одновременно с четырьмя specialist artifacts, а все четыре Unified API heads вернули `200`. Kaggle preprocessing 1.6.1 запускается под локальным scikit-learn 1.9.1 через узкий adapter для удалённых private cache `ColumnTransformer`/`SimpleImputer`; это не меняет веса и не является переобучением. После принятия решения по validation предусмотрена однократная изолированная final-оценка неизменённых весов и validation-порогов. Сравнение со специализированными моделями допустимо только на одинаковых заранее зафиксированных периодах **внутри каждой задачи**, с проверкой отрицательного переноса и отдельной калибровкой. Маршрутизатор не считается мультитаск-моделью.
